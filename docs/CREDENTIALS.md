# Credentials & API keys — what this build actually needs

Researched 2026-07-30 against developer.katanamrp.com and Katana support docs.

**Short version: you need exactly one key, and you already have it.** Everything else is
either auto-generated by the system, handled by a login-and-approve flow, or confirmed
not to exist. Details below.

---

## 1. Katana API key — HAVE IT ✅

The only credential a human creates by hand.

| | |
|---|---|
| Where | Katana web app → **Settings → API → Add new API key** |
| Format | `Authorization: Bearer <key>` |
| Stored as | `KATANA_API_KEY` in `.env` (gitignored) |
| Status | **Already generated and verified working** |

Katana's docs do **not** publish key scopes, expiry, revocation, or a per-account key
limit. Practical read: keys are full-access and long-lived. Two consequences —

- **Full access means full access.** This one key can delete products and orders, not just
  read them. Treat it like the master password to inventory.
- **Rotate it if it ever leaks**, and rotate on staff turnover. Generate the new key first,
  swap `.env`, then delete the old one — there's no documented grace period.

Rate limit is **60 requests/minute** (`X-RateLimit-Limit` header). Every script we write
throttles against this. A 2,000-SKU bulk load is ~35 minutes minimum.

## 2. Webhook secret — AUTO-GENERATED, no action ✅

Common misconception worth killing early: **you do not create this.** When we register a
webhook through the API, Katana returns a **secret token in the `token` field of the
response**. We store that token and use it to verify every incoming webhook is genuinely
from Katana.

- Header: `x-sha2-signature` (hex)
- Algorithm: **HMAC-SHA256**, keyed with the token, over the **raw request body**
- Gotcha: verify against the raw body *before* parsing JSON, or the signature won't match

Without this check, anyone who learns our webhook URL could post fake "sale happened"
events and trigger bogus replenishment shipments. It is not optional.

### Webhook events worth having (72 exist; these matter here)

| Event | Why we want it |
|---|---|
| `sales_order.created` | POS sale lands in Katana → starts the replenishment cycle |
| `current_inventory.product_updated` | Stock level moved at Vado |
| `current_inventory.product_out_of_stock` | **Fires the "critical stockout" trigger** from Finding 3 — no polling needed |
| `purchase_order.received` | Vado received the shipment → closes the loop (Phase 4) |
| `purchase_order.partially_received` | Short shipment — the case that silently corrupts stock counts |

`product_out_of_stock` is a genuinely useful find: trigger #3 in the replenishment plan can
be **event-driven instead of polled**, which is both faster and cheaper against the 60/min
rate limit.

### Prerequisite most people miss

Webhooks need a **public HTTPS URL** Katana can reach. That's a small hosted endpoint —
infrastructure, not a credential. If we don't want to run one, the fallback is polling
inventory on a schedule, which costs rate-limit budget but needs no server. **Decide at
Phase 3.** Not blocking anything now.

## 3. Shopify — ONLY IF we go that route, and it needs NO API key ⚠️

If the chrome shop ends up on Shopify POS (Finding 2), the Katana↔Shopify connection is
**OAuth through Katana's Integrations Marketplace** — a login-and-approve flow, not a
manually created token. Nothing lands in `.env`.

What's needed instead is **access**:
- Active Katana account (have it)
- **Admin** access to the Shopify store
- Connect from **Katana → Integrations Marketplace → Shopify → Connect → Authorize**

> Katana's docs are explicit: *"Always initiate new integrations from your existing Katana
> account"* — starting from the Shopify App Store side can create a duplicate subscription
> you'll pay for twice.

Setup then exposes tabs for Products, Inventory (**this is where Shopify POS locations map
to Katana locations** — Vado → Vado, not Weatherford), Orders, and Customers.

## 4. Comdata / Trendar / SmartStation — NO KEY EXISTS ❌

Confirmed dead end, don't spend time here. Comdata's developer portal
(resourcecenter.comdata.com) documents only:

API Developer Portal (account info, ordering/blocking cards, vehicles) · Web Services
1.0/2.0/2.1 · Mastercard Web Services · Proprietary Web Services · Vendor Enrollment ·
Virtual Card Web Services

**All fleet-card payments. Zero merchandise, PLU, SKU, or inventory endpoints.** Generating
a Comdata developer key does nothing for this project.

Store data, if we can get it, comes out of **SmartStation's report export** (brochure
confirms 40+ reports with export) as a file — not an API. That path needs a file location
and possibly SFTP or share credentials, which we'll only know once the export format is
confirmed. **Still pending the item-movement check at the store.**

## Note for later: OAuth 2.0 exists

Katana's docs include an **OAuth 2.0 Setup** guide alongside API keys. That's for apps
acting on behalf of *other* Katana accounts. Our integration is private and single-account,
so the API key is correct. Only revisit if this ever gets resold to other operators.

## Rules

- `.env` only. Never in code, never in chat, never in a file that isn't gitignored.
- `.env.example` lists variable **names** only — that one is committed.
- Server-side only. Katana's docs: keys "should never be exposed in client-side code."
